MXC for Ruby 0.2.0 limits what a sandboxed command can use, not only what it can reach: cap its CPU time and memory, lower its priority, and read back how much CPU time it used.

```sh
gem install mxc
```

Precompiled gems are available for Linux (x86_64 and ARM64, glibc and musl), macOS (Intel and Apple Silicon), and Windows (x64 and ARM64), for Ruby 3.2 through 4.0.

This release builds on [a fork of Microsoft's MXC](https://github.com/crmne/microsoft-mxc) that adds resource limits to MXC itself, until they land upstream: proposed in [microsoft/mxc#1498](https://github.com/microsoft/mxc/issues/1498) and submitted as [microsoft/mxc#1499](https://github.com/microsoft/mxc/pull/1499). Everything else behaves as in 0.1.0.

## New

### Cap CPU time and memory

```ruby
sandbox = MXC.sandbox.with_limits(cpu_time: 2.minutes, memory: 2.gigabytes)
result = sandbox.run("python3", "build.py")

result.limit_exceeded # => :cpu_time when the script spun until its budget ran out
```

Each process the command starts gets its own CPU time and memory. A process that uses up its CPU time is stopped, and an allocation beyond the memory limit fails. On Linux the memory limit covers the heap rather than the address space, so programs that reserve large regions up front, such as LibreOffice, still run. Limits also work as keywords and class macros:

```ruby
MXC.run("python3 build.py", limits: { cpu_time: 120, memory: 2 * 1024**3 })

class SkillSandbox < MXC::Sandbox
  limits cpu_time: 2.minutes, memory: 2.gigabytes
end
```

By @crmne

### Lower a command's priority

```ruby
MXC.run("python3 train.py", priority: :low)
```

`:low` and `:lowest` keep your app responsive while a heavy command runs. They map to nice 10 and 19 on Linux and macOS, and to the below normal and idle priority classes on Windows. By @crmne

### See how much CPU time a command used

```ruby
result = SkillSandbox.new.run("python3", "build.py")

result.cpu_time # => 3.42
result.inspect  # => "#<MXC::Result exit_code=0 timed_out=false cpu_time=3.42 limit_exceeded=nil backend=:bubblewrap>"
```

`cpu_time` counts user and system time of the command and every process it waited for, in seconds. Results from `MXC.run`, streaming runs, and `Process#wait` all carry it. By @crmne

### Limit the number of processes on Windows

```ruby
MXC.run("python build.py", limits: { processes: 16 })
```

Windows counts the processes of one sandbox, so a fork bomb stops at the limit and `limit_exceeded` reports `:processes`. By @crmne

### Ask the host which limits it enforces

```ruby
MXC.supports?(:cpu_time_limit) # => true
MXC.supports?(:memory_limit)   # => false on macOS
MXC.supports?(:process_limit)  # => true on Windows only
MXC.supports?(:priority)       # => true
```

A limit the host cannot enforce raises `MXC::UnsupportedError` with a remediation before anything starts. By @crmne

## Known limitations

* **CPU time and memory limits are per process, not per sandbox.** On Linux and macOS, MXC sets them with rlimits inside the sandbox rather than with cgroups, so a command that starts four workers gets four budgets. To bound the whole worker, use container limits such as Docker's `--memory`, `--cpus`, and `--pids-limit`; [Running in Docker](https://crmne.github.io/mxc/running-in-docker/#limiting-the-container) shows how.
* **No process limit on Linux or macOS.** Neither can count the processes of one sandbox without cgroups, and `RLIMIT_NPROC` counts every process of the user, so `processes` raises `MXC::UnsupportedError` there.
* **No memory limit on macOS.** macOS rejects memory rlimits, so `memory` raises `MXC::UnsupportedError` there.
* **Linux and macOS only report `:cpu_time` as the limit exceeded.** A program that cannot allocate memory decides itself how to fail, so read its exit code and `stderr`.
* **CPU time limits are rounded up to whole seconds on Linux and macOS.** Windows counts user-mode time only and checks it every few seconds, so a process there can run a little past its limit.
* **`cpu_time` is reported only for sandboxes with limits or a priority.** Other runs take the same path as in 0.1.0 and report `nil`.
* **On Linux, a sandbox with limits or a priority runs the command as the first process of its sandbox,** so the command ignores signals sent from inside the sandbox that it has no handler for.
* **The resource limits come from a fork of MXC.** The changes are proposed upstream in [microsoft/mxc#1498](https://github.com/microsoft/mxc/issues/1498), and the gem will move back to the released `mxc-sdk` crate once MXC ships them, without changing this API.
