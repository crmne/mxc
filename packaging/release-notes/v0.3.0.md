MXC for Ruby 0.3.0 runs sandboxes on Linux hosts that block the user namespaces Bubblewrap needs, such as a default Docker container or Ubuntu with AppArmor's restriction on, by running them on Landlock instead.

```sh
gem install mxc
```

Precompiled gems are available for Linux (x86_64 and ARM64, glibc and musl), macOS (Intel and Apple Silicon), and Windows (x64 and ARM64), for Ruby 3.2 through 4.0.

This release builds on [a fork of Microsoft's MXC](https://github.com/crmne/microsoft-mxc) that adds a Landlock backend to MXC itself, for [microsoft/mxc#1494](https://github.com/microsoft/mxc/issues/1494), on top of the resource limits 0.2.0 introduced.

## New

### Sandboxes where Bubblewrap cannot run

```ruby
result = MXC.run("python3 build.py", readable: "app/skills", writable: "tmp/out")

result.backend  # => :landlock in a default Docker container
result.warnings # => ["Bubblewrap cannot run on this host, so containment \"process\" runs on Landlock instead. ..."]
```

With the default `backend: :auto`, a Linux host where Bubblewrap cannot create its namespaces now runs the sandbox on [Landlock](https://docs.kernel.org/userspace-api/landlock.html), which needs no namespaces, privileges, or helper programs, only Linux 6.2 or newer. The same filesystem policy, timeout, CPU time and memory limits, and priority apply. A policy Landlock cannot hold is refused with `MXC::UnsupportedError`, never run with less protection. By @crmne

### Choose Landlock or Bubblewrap

```ruby
MXC.run("python3 build.py", backend: :landlock)
MXC.configure { |config| config.backend = :bubblewrap } # never falls back
```

`:landlock` asks for Landlock on any Linux host, and `:bubblewrap` keeps the 0.2.0 behavior of failing where Bubblewrap cannot run. By @crmne

### Know which backend your sandboxes run on

```ruby
MXC.availability.runs_on # => :bubblewrap, or :landlock
MXC.supports?(:network)  # => false where sandboxes run on Landlock
MXC.backends.map(&:name) # => [:bubblewrap, :landlock]
```

By @crmne

## Fixed

* **A command that exits with status 1 and prints a line starting with `bwrap:` is a result again, not an error.** The gem now learns that Bubblewrap could not start a sandbox from Bubblewrap itself rather than guessing from the exit status and output. By @crmne

## Known limitations

* **No network on Landlock.** Landlock cannot tell one address from another, so it could only allow the whole host network, including the host's loopback and inbound connections. `network: true` and host allow-lists raise `MXC::UnsupportedError` there. Use Bubblewrap for commands that need the network.
* **No metadata changes by name on Landlock.** Landlock does not govern metadata, so MXC refuses permission, owner, timestamp, and extended attribute changes by path there, even in `writable` paths: `chmod +x` and `touch` of a file the command may only read fail. Changes through a file the command opened, and `touch` of a file it may write, still work.
* **No denied paths inside granted ones on Landlock.** Landlock grants whole directory trees, so a `denied` path inside a `readable` or `writable` one raises `MXC::UnsupportedError`.
* **No private `/dev/shm` on Landlock,** so POSIX semaphores, and Python's `multiprocessing` locks, fail with `Permission denied`.
* **Landlock and its fallback come from a fork of MXC,** as the resource limits do, until MXC ships them.
