MXC for Ruby 0.4.1 is a security release. Bubblewrap sandboxes no longer let the command they run read your application's environment. Upgrade now if you run Bubblewrap on Linux without `limits`.

```sh
gem install mxc
```

Precompiled gems are available for Linux (x86_64 and ARM64, glibc and musl), macOS (Intel and Apple Silicon), and Windows (x64 and ARM64), for Ruby 3.2 through 4.0.

## Upgrade if you run Bubblewrap on Linux without `limits`

**Every sandbox on Linux's Bubblewrap backend that sets no limits could read your application's environment, in 0.1.0 through 0.4.0.** A command in such a sandbox could read the full environment of the process that started it, including API keys, from `/proc/1/environ`. That covers variables from the process environment and those set with `ENV[]=` before the run. It applies with a fresh or a bound `/proc`, with or without network. Checking the environment from inside the sandbox shows nothing wrong.

**Treat secrets in that environment as exposed if you ran untrusted code without limits, and rotate them.** That includes code written by a language model and code uploaded by users.

Sandboxes with `limits` (0.2.0 and later) and sandboxes on Landlock were not affected.

If you cannot upgrade yet, do either of these:

* Set a limit on every sandbox, such as `limits: { cpu_time: 60 }`, on 0.2.0 or later.
* Start the process that runs sandboxes with a clean environment, such as `env -i PATH="$PATH" bin/jobs`, read secrets from files or a secret store, and do not put them in `ENV`.

## Fixed

### Bubblewrap starts with a clean environment

`--clearenv` only cleans the command's environment. Bubblewrap's own process stays in the sandbox as PID 1, with the command's user and user namespace, and keeps the environment it was started with. Bubblewrap and the network supervisor now start with only `PATH` and the settings of the Docker wrapper. `env` keeps working as before. By @crmne

### The Docker wrapper keeps Bubblewrap's options off its command line

[`bwrap-wrapper.sh`](https://github.com/crmne/mxc/blob/v0.4.1/docs/assets/docker/bwrap-wrapper.sh) now hands Bubblewrap its options through a descriptor, so other sandboxes in a container with a bound `/proc` cannot read the policy's paths or the variables set with `env`. Copy the new wrapper into your image. By @crmne

### A path can be both readable and writable

A subclass that makes a parent's readable path writable now writes to it. Fixes [#4](https://github.com/crmne/mxc/issues/4). By @crmne

## Known limitations

* **A sandbox does not always hide other processes.** On Landlock, on Seatbelt, and with a bound `/proc`, a command can read the command lines of other processes, including other sandboxes running at the same time. On macOS it can also read the environment your application started with, though not variables set later from Ruby, and we found no Seatbelt rule that blocks it, so start your application with only the secrets it needs at launch. Windows has not been assessed. [Policies](https://crmne.github.io/mxc/policies/#what-the-command-can-see-of-other-processes) lists what each backend shows.
